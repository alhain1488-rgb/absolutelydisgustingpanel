# ROADMAP — план автономной реализации

Это исполняемый план для Claude Code. Идём **строго по фазам**. Внутри фазы — свобода.
Ритуал завершения каждой фазы (обязателен): прогнать проверки → всё зелёное → `git commit`
(Conventional Commits) → запись в `docs/PROGRESS.md` → следующая фаза.

Работаем в ветке `build/mvp` (не в `main`), чтобы человек мог ревьюить историю коммитов.

Условные обозначения: **Цель** — что делаем; **Готово, когда** — критерии приёмки, которые
можно проверить командой.

---

## Фаза 0 — Архитектура и каркас  ⟵ точка ревью человеком

**Цель.** Зафиксировать архитектуру и поднять пустой скелет проекта.

- `docs/ARCHITECTURE.md` — решения и их обоснование (SSH-конфиг-механизм, реестр протоколов,
  модель доступа через inbound-ы, шифрование секретов).
- `docs/ERD.md` — ER-диаграмма (mermaid) из `SPEC.md §4`, при необходимости уточнённая.
- `docs/openapi.yaml` — контракт API (скелет всех эндпоинтов из `SPEC.md §10`).
- Скелет каталогов из `SPEC.md §11`, `go.mod`, `package.json`, `docker-compose.yml`,
  `.env.example`, `.gitignore`, `deploy/Caddyfile`, пустой `docs/PROGRESS.md` и `docs/QUESTIONS.md`.

**Готово, когда:** `docker compose config` валиден; `go build ./...` и `npm run build` проходят
на пустом скелете (заглушки); все файлы Фазы 0 закоммичены.

> После этой фазы человек может просмотреть архитектуру по коммиту. Дальше фазы идут автономно.

---

## Фаза 1 — Фундамент backend

**Цель.** Конфиг, БД с автомиграциями, шифрование, логирование, health.

- `config` — чтение и валидация env (`PANEL_ENCRYPTION_KEY`, `PANEL_ADMIN_USERNAME`,
  `PANEL_ADMIN_PASSWORD`, `PANEL_DOMAIN`, `PANEL_JWT_SECRET`, `DB_PATH`, …). Отсутствие
  обязательного — понятная ошибка на старте.
- `db` + `migrations` — схема из `SPEC.md §4`, миграции применяются автоматически при старте.
- `crypto` — AES-256-GCM (encrypt/decrypt) и bcrypt-обёртки.
- `logging` — структурный логгер.
- `httpapi` — сервер, `/healthz`, `/readyz`.

**Готово, когда:** `go test ./...` зелёный (миграции применяются на чистой БД; AES round-trip;
bcrypt verify); `docker compose up` поднимает backend, БД мигрирует, `curl /healthz` → 200.

---

## Фаза 2 — Аутентификация и аудит

**Цель.** Вход админа, 2FA, журнал действий.

- Логин по bcrypt; сессия (JWT+refresh или cookie); middleware авторизации.
- TOTP: setup (otpauth-URL + QR), enable, verify. Секрет хранится зашифрованным.
- `audit` — middleware/хелпер, пишет все админ-действия в `audit_logs`.
- Первичный админ создаётся из env при первом старте.
- Rate-limit на логин.

**Готово, когда:** тесты на логин (успех/провал), полный цикл TOTP (setup→enable→verify),
запись в аудит; вручную через Swagger можно войти и включить 2FA.

---

## Фаза 3 — Управление серверами

**Цель.** CRUD серверов, SSH, метрики, статус и рестарт Xray.

- CRUD `servers`; SSH-секрет шифруется при сохранении.
- `ssh` — клиент за интерфейсом (`Runner`): подключение по ключу/паролю, exec.
- Проверка доступности; IP + геолокация; определение статуса Xray; снятие CPU/RAM/диск.
- `POST /check`, `/restart-xray`, `/stats`.

**Готово, когда:** юнит-тесты с мок-`Runner` (парсинг метрик, статуса, обработка ошибок SSH);
CRUD покрыт тестами; через Swagger (против мока) можно добавить сервер, увидеть статус, дернуть рестарт.

---

## Фаза 4 — Inbound-ы и реестр протоколов

**Цель.** Inbound-ы разных типов и сборка их в конфиг Xray.

- CRUD `inbounds` (в рамках сервера); протокол-параметры в JSON; генерация ключей Reality на бэкенде.
- `protocols` — реестр + адаптеры: VLESS Reality, VLESS TLS, VMess, Trojan, Shadowsocks.
  Каждый умеет `BuildInbound` и `BuildLink`. (Hysteria2 — заглушка, см. `SPEC.md §5`.)
- Валидация: сборка объекта inbound для ≥3 протоколов проходит `xray -test` на локальной ноде.

**Готово, когда:** тесты реестра (каждый адаптер строит валидный inbound и корректный URI);
интеграционный тест против `test/xray-node`: сгенерированный конфиг с VLESS Reality + VMess + Trojan
принимается `xray -test`.

---

## Фаза 5 — Клиенты, доступы и подписка

**Цель.** Клиенты, выдача доступа к inbound-ам, подписка, sync-движок.

- CRUD `clients`; генерация UUID/password/токена; enable/disable.
- Выдача/отзыв доступа: `PUT /clients/{id}/inbounds` (связь `client_inbounds`).
- `subscription` — `GET /sub/{token}`: сборка base64-подписки из всех разрешённых/включённых
  inbound-ов клиента на всех серверах; QR; скачивание конфига; `rotate-token`.
- `sync` — движок: сборка полного `config.json` сервера, бэкап → запись → `xray -test` → рестарт;
  идемпотентность по хэшу; запись `last_sync_*`.

**Готово, когда:** e2e-тест: создать клиента → выдать 2 inbound-а на разных серверах → `/sub/{token}`
возвращает валидную непустую подписку с обоими URI; отзыв доступа/disable убирают их из подписки;
sync против `test/xray-node` пушит и проходит `xray -test`.

## Фаза 6 — Frontend

**Цель.** Полный UI, подключённый к API.

- Login (+ шаг TOTP), Dashboard (карточки серверов, метрики, счётчики, время синхронизации),
  Servers/ServerDetail (inbound-ы, проверить/рестарт), Clients/ClientDetail (чекбоксы inbound-ов,
  ссылка, QR, скачать, обновить), Settings (домен/тема/2FA), Logs.
- Тёмная/светлая тема. Современный минимализм.
- Типы API синхронизированы с `openapi.yaml`.

**Готово, когда:** `npm run build` и `npm run test` зелёные; при поднятом backend все страницы
работают против реального API; переключение темы работает.

---

## Фаза 7 — Сборка, документация, доставка

**Цель.** Один `docker compose up`, полный Swagger и README.

- Полный `docs/openapi.yaml` в синхроне с кодом; Swagger отдаётся на `/swagger`.
- Caddy: TLS (авто-Let's Encrypt по `PANEL_DOMAIN`) + reverse proxy на backend и статику фронта.
- `README.md`: назначение, требования, быстрый старт (`cp .env.example .env` → заполнить →
  `docker compose up`), описание переменных окружения, как подключить реальный VPS, как добавить
  новый протокол (через реестр), troubleshooting.
- Smoke-скрипт из `SPEC.md §12`.

**Готово, когда (= Definition of Done проекта):** на чистой машине `cp .env.example .env`
(человек вписывает секреты) → `docker compose up` → панель по HTTPS → вход с TOTP, добавление
сервера, inbound-ы, создание клиента, рабочая subscription-ссылка + QR, статистика на дашборде;
Swagger доступен; все тесты и линтеры зелёные; README полный.

## Что требует человека (Claude Code сам это НЕ делает)

Эти пункты Claude Code должен явно оставить человеку (и, где нужно, записать в `docs/QUESTIONS.md`),
а не пытаться выполнить автономно:

1. **Заполнение `.env`** реальными секретами (мастер-ключ шифрования, JWT-секрет, логин/пароль
   админа, домен). Claude Code готовит `.env.example` и падает с понятной ошибкой, если чего-то нет.
2. **Реальные SSH-ключи и доступ к трём VPS.** Разработка и тесты — только на моках и локальной
   dockerized-ноде Xray. «Наведение» панели на реальные серверы — вручную человеком.
3. **DNS/домен и выпуск TLS-сертификата** (Caddy сделает авто-выпуск, но домен должен вести на VPS).
4. **Решение по Hysteria2**, если он нужен (в MVP не поддержан, см. `SPEC.md §5`).
5. **Финальный деплой на прод** — человеком, после ревью.
