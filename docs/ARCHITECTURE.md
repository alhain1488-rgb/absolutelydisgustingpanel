# ARCHITECTURE — решения и обоснование

Документ фиксирует ключевые архитектурные решения панели управления Xray и их
обоснование. Читается вместе с `SPEC.md` (что строим) и `ROADMAP.md` (порядок).

## 1. Механизм управления Xray на нодах: SSH + файл конфига

**Решение.** Панель управляет каждым Xray-сервером, генерируя полный `config.json`
и доставляя его по SSH: бэкап текущего файла → запись нового → `xray -test` →
рестарт сервиса. Runtime gRPC HandlerService в MVP не используется.

**Обоснование.**
- Прямо покрывает требования ТЗ: «перезапуск Xray из интерфейса», «CPU/RAM/диск
  по SSH», «регенерация и пуш конфига при изменении».
- Один источник истины — БД панели. Конфиг ноды всегда детерминированно
  собирается из inbound-ов сервера и выданных клиентам доступов.
- Проще и надёжнее runtime-API: нет частичного состояния, любое изменение — это
  атомарная замена файла с валидацией до рестарта.
- Идемпотентность: перед пушем сравниваем SHA-256 нового конфига с последним
  применённым; пустые пуши пропускаем.

**Граница.** Горячее добавление клиентов через gRPC без рестарта — возможное
будущее улучшение, в MVP не делаем.

## 2. SSH за интерфейсом (`Runner`)

Весь доступ к серверам идёт через интерфейс `Runner` (`internal/ssh`):

```go
type Runner interface {
    Run(ctx context.Context, cmd string) (stdout, stderr string, err error)
    Upload(ctx context.Context, remotePath string, content []byte, mode os.FileMode) error
}
```

Реальная реализация — на `golang.org/x/crypto/ssh`. В юнит-тестах — мок. Так
бизнес-логика (парсинг метрик, статуса Xray, sync-движок) тестируется без реальной
инфраструктуры, а интеграция проверяется на локальной dockerized-ноде в `test/xray-node`.

## 3. Реестр протоколов

Знание о протоколе живёт в одном месте — интерфейс `Protocol` + реестр
`map[string]Protocol` (`internal/protocols`). Каждый адаптер умеет `BuildInbound`
(объект inbound для `config.json`) и `BuildLink` (subscription-URI). Добавить
протокол = реализовать интерфейс и зарегистрировать. **Схема БД при этом не меняется.**

MVP: VLESS Reality, VLESS TLS, VMess, Trojan, Shadowsocks. Hysteria2 — заглушка
(в xray-core inbound-а нет, см. `SPEC.md §5`).

## 4. Модель доступа через inbound-ы

Клиент получает доступ не к серверу целиком, а к конкретным inbound-ам. Связь
`clients` ↔ `inbounds` — многие-ко-многим через `client_inbounds` с уникальностью
`(client_id, inbound_id)` и собственным `enabled` для точечного отзыва. Подписка
собирается автоматически из всех разрешённых и включённых inbound-ов клиента на
всех серверах.

## 5. Протокол-специфичные параметры в JSON

Таблица `inbounds` хранит общие поля (tag, protocol, listen, port, enabled) как
колонки, а всё протокол/транспорт/security-специфичное (ключи Reality, flow, SNI,
ALPN, ws/grpc path) — в JSON-полях `settings_json` / `stream_settings_json` /
`sniffing_json`. Это и есть механизм «новый протокол без ALTER TABLE».

## 6. Шифрование секретов at-rest

AES-256-GCM, мастер-ключ из `PANEL_ENCRYPTION_KEY` (32 байта, base64).
Шифруются: SSH-ключ/пароль (`ssh_secret_enc`), SSH-passphrase
(`ssh_passphrase_enc`), TOTP-секрет (`totp_secret_enc`). Пароль админа хранится
только как bcrypt-хэш (cost 12), не шифруется и не расшифровывается.

Формат шифротекста: `base64( nonce(12) || ciphertext || tag )`. Ключ читается из
env один раз при старте; отсутствие/неверная длина — фатальная ошибка старта.

## 7. Слой БД и переносимость на Postgres

SQLite (файл в volume). Миграции — аддитивные `*.up.sql`/`*.down.sql`,
применяются автоматически при старте. Доступ к данным — через типобезопасный
слой (sqlc); бизнес-логика не содержит SQLite-специфичных хаков, чтобы переход на
Postgres требовал минимальных правок. Уже применённую миграцию не редактируем.

## 8. HTTP-слой

`chi`-роутер. Группы: `/api/*` (защищённые JWT), публичный `/sub/{token}`,
служебные `/healthz` `/readyz` `/swagger`. Middleware: логирование, восстановление
после паники, аутентификация, аудит админ-действий, rate-limit на логин и `/sub`.
Контракт — design-first в `docs/openapi.yaml`, Swagger отдаётся на `/swagger`.

## 9. Развёртывание

Docker Compose: `backend` (Go), `frontend` (статика React, собранная в образ) и
`caddy` (TLS via Let's Encrypt по `PANEL_DOMAIN` + reverse proxy на backend и
статику). Один `docker compose up` поднимает всё.
